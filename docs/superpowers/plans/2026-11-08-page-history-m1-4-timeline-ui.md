# Page history M1.4: timeline UI, version view and Show changes (implementation plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** From the combined page-history release on, the History drawer is the design's timeline: day headings, one entry per editing session (and per restore, copy, import, template, gap and pre-rollout version) with who, when and how many words, loaded as the editor scrolls; clicking an entry shows the page as it was right after it, rendered read-only with the real editor styles, with that entry's own changes highlighted; the old snapshot list and its 5 + 1/day snapshot retention are gone (3 newest snapshots per page are kept as a boot cache).

**Architecture:** The server renders every past version as ProseMirror JSON (`pm_json`, parity-tested against y-tiptap's `yXmlFragmentToProsemirrorJSON`) from M1.3's window replay (`pass::replay_window`), and "Show changes" as the same union-doc diff the stored word counts come from (`diff::entry_diff`), so no Y data for a past state reaches the client. A `Views` service in `crates/knot-history` loads an entry's replay input inside a read-only transaction, renders it on an isolated thread holding a compute permit of the builder's shared `HistoryPermits` (whose builder pacing no longer holds compute permits, so a view waits only for the computes running or already queued when it arrived, at most one builder compute per worker), and caches serialized results keyed on the entry's `updated_at`. The web drawer is rebuilt in `web/src/features/docs/history/` on the keyset list API (M1.3) and a read-only Tiptap editor built from the live schema plus `historyInsert`/`historyDelete` marks and a `historyChange` node attribute.

**Tech Stack:** Rust (yrs 0.27.3, sqlx 0.9, tokio, axum 0.8, moka 0.12), Postgres 18, React 19 + Tiptap 3.31.3 + @tiptap/y-tiptap 3.0.9 + TanStack Query 5 + valibot (web/), vitest, Playwright (e2e/), Helm chart docs.

## Review Focus

1. **A view asked for while the builder is busy, or while the reader clicks quickly through versions** (the post-upgrade backlog: 20 passes queued per loop, the default single worker, pacing sleeps). The editor expects the version within seconds, not after the queue drains or behind renders nobody looks at any more. The bound is the computes running or already queued for a permit when the view arrives: earlier views, plus at most one builder compute per worker (builder slots), which for a large page's genesis can outlast the client's retries (Rulings). Pinned in Task 4 (`a_view_waits_for_at_most_one_builder_compute_per_worker`, `a_view_queued_after_a_builder_waits_for_its_compute`, `pacing_holds_the_builder_slot_not_the_compute_permit`, `the_lease_is_renewed_while_the_build_waits_for_a_permit`), Task 5 (`a_busy_permit_is_busy_after_the_wait`, `a_dropped_view_request_cancels_its_render`) and Task 12 (`a superseded view request is aborted`).
2. **An open session that grows while the drawer is open.** Its `end_rev` rises, so it can move above a page cursor the client already used, and its view must follow its new end, not a cached older one. The entry must not vanish from the timeline, its view must show the latest text without blanking the pane in between, and a restore must not restore text the reader has not seen. Pinned in Task 5 (`an_open_sessions_view_follows_its_new_end`), Task 7 (`a_restore_of_a_moved_entry_is_a_409`), Task 11 (`a_session_that_moved_above_the_cursor_reappears_after_the_poll`, `a failed poll keeps the loaded timeline`) and Task 12 (`a_selected_open_session_refetches_when_its_end_moves`, `keeps the old version visible while the new end loads`, which also counts exactly two viewer mounts). Residual (Rulings): a late gap credit raises a session's `end_rev` without moving its `ended_at`; neither the client's view key nor the restore check sees that.
3. **A past version the current editor cannot show as stored, or whose diff cannot be built** (a tag or mark the schema no longer has, an empty page, a mark stored as `true`, an attribute stored as a string, linked or bold inline code from an import, stray text or an empty container the old importer or a merge left, a change inside a code block or inline code, a diff step that fails or panics). The drawer must show the version as the live editor would, a placeholder, or "This version can't be shown.", never crash or blank the drawer, and never fail a version only because Show changes is on. Pinned in Task 1 (`unknown_tags_become_a_placeholder_paragraph`, `unknown_inline_elements_become_placeholder_text`, `root_text_is_flattened`, golden cases `unknown-mark`, `empty-doc`, `import-code-link`, `import-code-bold`, the Import-shape and damaged corpus in `pm_json_matches_y_tiptap_on_the_markdown_corpus`), Task 2 (`changes_inside_code_are_marked`, `an_unchanged_diff_render_is_pm_json_on_every_fixture_case`, `an_added_paragraph_with_unknown_content_keeps_pm_jsons_rules`: the default view is `pm_json_diff`'s output, so each `pm_json` shape rule is pinned for it too), Task 3 (`a_diff_that_panics_falls_back_to_the_plain_render`), Task 5 (`a_diff_that_fails_falls_back_to_the_plain_view`), Task 9 (`every rendered fixture case is viewable`, `linked and bold inline code is strict`, `stray text and empty containers render leniently`, `history marks render inside code blocks and inline code`), Task 12 (`a_version_the_schema_rejects_says_it_cant_be_shown`, `an_empty_version_renders_an_empty_paragraph`, `a_version_with_edited_code_renders_with_changes`, `a version with stray text renders as the live editor shows it`, `a version shown without changes says so`).
4. **A very large page or entry, or an input known to hang.** A view over the plain cap answers 409 with a clear message and no allocation of the whole input; a Show changes view over only the lower diff cap shows the plain version (`changes: false`), so the default view never reads as unviewable for a version that fits the plain cap; plain views and restores use the plain cap, so a page that can be built can still be restored; a render that hangs releases the request after `VIEW_TIMEOUT` while its thread keeps its permit, and the same version is not replayed into the same hang again (a diff that timed out, or a session whose word count the builder could not take, is shown plain; a plain render that timed out answers 500 until the TTL), also when the reader clicked away before the timeout (the dropped request's thread is watched and recorded once it outlives the timeout); a restore that timed out blocks restores only, never the version's view; a session whose count is still being taken is not mistaken for one whose count failed; a baseline the builder skipped is never replayed. Pinned in Task 5 (`over_the_cap_is_too_large`, `plain_views_and_restores_use_the_plain_cap`, `a_skipped_baseline_is_not_replayed`, `a_render_that_panics_fails_and_one_that_hangs_times_out_and_keeps_its_permit`, `a_diff_that_hangs_is_not_tried_again`, `a_dropped_render_that_outlives_the_timeout_is_not_replayed`, `a_session_the_builder_could_not_count_is_shown_plain`, `a_session_being_counted_is_not_shown_plain`, `restore_input_is_bounded_like_a_plain_view`), Task 6 (`a_skipped_baseline_is_a_500`, `a_view_over_the_cap_is_a_409`) and Task 12 (`a_too_large_version_says_so`, `a version shown without changes says so`).
5. **Snapshots thinned before the builder gap-checked them** (builder lagging after the upgrade, or `history.workers: 0`). Content only those snapshots hold would never reach history. Pinned in Task 8 (`thinning_keeps_snapshots_the_builder_has_not_probed`, `thinning_keeps_at_most_32_unprobed`).

Also pinned, beyond the five: a restricted page refuses view and restore to an Editor without a grant, and an entry id of another page never restores (Tasks 6 and 7); a builder that gives up its permit wait in the words phase keeps that session's count pending and its page dirty, also on a page the sweep claimed for an idle session (Task 4, with the pass compute let through first so the expired wait is the words phase's); a past version's task checkboxes cannot be ticked in the viewer (Task 9, `a_viewer_task_click_changes_nothing`); every view outcome, the view timeout counter, the stalled gauge and the render histogram are recorded (Task 5), so the README's alert can fire.

- Ruling: M1.4 keeps restore working by re-keying today's Markdown restore from a snapshot seq to a timeline entry, at the architecture's final route `POST /api/docs/{id}/history/entries/{eid}/restore` (Task 7): the entry's state is replayed exactly as its view, serialized to Markdown and sent as `Event::ReplaceWithMarkdown` with source `restore` and meta `{target_entry_id, target_rev, target_ended_at}` (M2's shape, which the list already renders); "Restore as new page" and "Erase from history" are not built — retiring the snapshot list (task brief, architecture milestones M1.4) leaves today's seq restore without any client, and shipping the combined release without restore would remove a feature 0.9.10 has; the round trip has exactly today's loss profile, and M2 replaces the handler body with the verified revert behind the same request — cost if wrong: one task of server code whose body M2 rewrites; drop Task 7 and the `Restore here` button stays hidden (`can_restore` gates it) if the user wants the combined release view-only.
- Ruling: `GET /api/docs/{id}/history` stops listing snapshots but keeps answering, with a JSON `[]`, until M2 removes it with the seq routes, and the list keeps its M1.3 path `/history/entries` — M1.3's ruling allowed either; moving the list to `/history` would hand a cached 0.9.10 bundle (rolling deploy) a JSON shape its validator does not expect; removing the route is not an option either: `router_with_state` merges `static_files::router`, whose `fallback_service` serves `index.html` with `200` for any unmatched path (`static_files.rs:26-36`), so the 0.9.10 drawer's `apiFetch` would get the HTML as a string and its `snaps.map(...)` would throw during render (`HistoryDrawer.tsx:38-39, 66`); `[]` makes that drawer show "No snapshots yet" until reload. A new bundle that reaches a 0.9.10 pod for `/view` during the rollout gets that HTML too: the view's valibot `parse` rejects it and the pane shows "This version can't be shown." until the pod is replaced — cost if wrong: one trivial handler kept one release longer.
- Ruling: views share M1.3's compute permits, but the builder's pacing sleep holds a builder slot (`HistoryPermits::builder_slot`, `workers` of them, a second, non-compute semaphore) instead of a compute permit, and the builder takes a compute permit per compute instead of once per `build_page` — tokio's `Semaphore` is FIFO, so with the M1.3 arrangement a view queued behind up to `CLAIM_LIMIT` (20) builder tasks per loop and behind every pacing sleep, i.e. minutes during the post-upgrade backlog; with builder slots, at most `workers` builder tasks ever wait for or hold a compute permit, so a view waits for at most the computes running or already queued when it arrived: the views ahead of it plus at most one builder compute per worker (a builder that claimed, loaded and queued before the view goes first, FIFO; with one worker that is one rows-budget pass of up to 10 s, or a genesis bounded only by `REPLAY_TIMEOUT`); views do not jump that queue (a priority gate, i.e. a builder that yields its permit to every waiting view, can starve the builder under steady viewing and adds a second ordering rule to the one FIFO queue; the bounded wait above is enough for a reader); the rule "After M1.3" binds is one *compute* semaphore per process, which holds: the builder slots gate no replay, so this relaxes only the letter of "no second semaphore", and Task 14's deviation note says so; compute permits stay `workers`, so `workers × F × cap` still bounds replay memory (a builder task waiting for its permit holds its loaded input, at most `workers × cap` more, 1× not F×) — cost if wrong: views add CPU beyond `history.cpuShare` while the builder sleeps (they are user-initiated and bounded by `VIEW_TIMEOUT`), and the builder change must keep every M1.3 builder test green.
- Ruling: a builder waits for its compute permit *after* its claim (the claim and the input load need no permit, which keeps the permit queue to computes that are ready to run), so the wait must not outlive the lease: `Run::compute` creates the acquire future once, pins it (`tokio::pin!`) and polls it in a `tokio::select!` loop against `sleep(lease / 3)` and a `compute_wait` deadline, renewing the lease on each tick (dropping a tokio `acquire_owned` future leaves the queue, so a new future per tick would send the builder to the back every `lease / 3`; a lost renewal ends the pass through `lost()`, as today), renews once more when the permit is granted (the compute then gets a full lease, M1.3's `replay_timeout + 30 s` margin), starts the compute's clock only then (the call sites record `knot_history_replay_seconds` from the duration `compute` returns, and pacing adds only that duration, so queueing is neither measured as replay time nor paced), and gives up after `BuildLimits::compute_wait` (default `LEASE`): it then ends the pass `PassResult::Busy` through the new `store::release_unfinished(pool, me, &[doc_id], PERMIT_WAIT, repend_words)` (`release_on_shutdown` generalized: `claimed_by`/`claimed_until` cleared, `failures = greatest(failures − 1, 0)`, `retry_after` NULL, `last_error = $reason`; `PERMIT_WAIT = "waited too long for a replay slot"`). In the words phase the entry was already taken (`take_words_entry` clears `words_pending` before the load, so each count is attempted once), so the same transaction sets `words_pending = true` again for that entry (`repend_words`, the taken entry's id; `&[]` in `genesis` and `pass`) and sets `doc_history_heads.dirty = true` for its page: a wait that expired is not an attempt, and without both the session would keep NULL counts for good. `dirty` is not always set at that point: `claim` never sets it, `release_in` recomputes it (`head_rev > built_rev OR EXISTS words_pending`, `store.rs:565-587`), and the common way a session seals is the sweep claiming an idle open session (`sweep_candidates`' idle arm, `store.rs:1746-1758`) on a page the last `release_in` left clean; that pass seals the session and `write_pass` returns `WordsPending` without a release (`store.rs:1494-1501`), so a re-pend without `dirty` would leave a page that `claim`'s clean check (`store.rs:312-316`) answers `Clean` and the idle arm no longer selects. The statement order is binding (store.rs lock order): the state `UPDATE … WHERE claimed_by = $me RETURNING doc_id` first (its row lock), then the entries re-pend and the heads `dirty` update, both restricted to the returned doc ids, so only the lease holder's pages are touched. In `genesis` and `pass` an expired wait changes nothing else: the page is claimed again because its heads are dirty, a late snapshot or an idle session, all still true. A graceful shutdown (every rolling upgrade) that aborts a pass during that same wait re-pends it too: the taken entry is recorded in `Builder::words_waiting` (`Arc<Mutex<HashMap<Uuid, i64>>>`, doc id → entry id) right after `take_words_entry` and removed when the permit is granted (the compute is then the attempt) and on every return path of the words phase, but not on drop, so an aborted pass leaves it there; `release_on_shutdown(ids)` passes the recorded entries of `ids` as `repend_words` and clears them. A stale record (a pass that ended by a panic between take and grant) re-pends a session at most once more, which only recounts it. The crash marker (`failures + 1`, `retry_after`, `pass interrupted`) is in place during the wait as during every other part of a pass: a process crash while waiting counts as one interrupted pass (M1.3's rule for a crash anywhere in a pass); an expired wait does not count. An unbounded wait cannot happen: a view thread that stalled with the only permit makes builds give up after `compute_wait` each, the stalled gauge says so, and the Helm README's advice (restart when it stays above 0) applies — cost if wrong: during a stall a page is claimed for up to 5 min per attempt and then retried.

- Ruling: a `changes=1` view skips the diff and is answered with the plain render (`changes: false`, outcome `no_changes`, no WARN log: nothing failed) when (a) its replay input is over the diff cap but within the plain cap, (b) it is a sealed `session` whose count the builder attempted and left NULL (`sealed && !words_pending && words_added IS NULL`; the words phase leaves exactly that after `too_large`, `diff_error`, `corrupt`, `gap_state`, `panic` or `timeout`, `builder.rs:1184-1250`; an open session has `words_pending` false and NULL counts too, hence `sealed`; and no builder holds the page's lease, `NOT coalesce(doc_history_state.claimed_until > now(), false)`: `take_words_entry` writes that same state *before* the load (`store.rs:1559-1580`) and `write_words` fills the counts only after the compute, a window that lasts through the load, the compute (up to `WORDS_TIMEOUT`, 60 s) and, after Task 4, the words phase's permit wait (up to `compute_wait`), all under a live lease that Task 4 renews while waiting; a view in that window tries the diff (the builder does the same work), and a count that then really fails leaves the lease released, so the next view is plain; a true hang of the diff in that window costs one timed-out view, which (c) then records), or (c) a Show changes render of the same key timed out within `VIEW_CACHE_TTL` in this process; for (a)–(c) the view looks up and fills the *plain* key (effective `changes = false`), so the plain cache entry serves both requests. A plain render that times out records the plain key, and a later plain view, Show changes view (downgraded to that key) or restore of it answers `ViewError::Failed("an earlier render of this version timed out")` (500 `history.view_failed`, outcome `failed`) before any permit or replay. A restore replay that times out records the *restore* key (`ViewKey::variant = Restore`), which only later restores check (together with the plain key): `RESTORE_TIMEOUT` (15 s) is shorter than `VIEW_TIMEOUT` (20 s) and a restore also runs the Markdown round trip, so its timeout is no evidence that the plain render hangs, and a version that renders in 16 s must stay viewable. The record is `Views::timed_out`, a `moka::sync::Cache<ViewKey, ()>` of at most 1,024 keys with `VIEW_CACHE_TTL`, written by the init future (or `restore_input`) on a timeout and by the stall watcher of a dropped request whose thread outlives its timeout (Rulings on cancellation) — the default view is `changes=1`, and the design says any entry can be viewed, so a version that fits the plain cap must not answer 409 only because Show changes is on; and the diff step's union-doc build and `encode_state_from_snapshot` are not cancellable, so a diff that hangs holds a compute permit for its thread's whole life: with the default single worker each new click on that entry would answer every other view 503 and make every build wait out `compute_wait`; the builder already measured those sessions (its words timeout is 60 s, `builder.rs:1244-1252`), and the key includes `updated_at`, so an open session that is extended is tried again — cost if wrong: a session whose count failed transiently (a timeout under load) is not highlighted until a rebuild; a true hang is retried once per process and TTL; an earlier version with a plain render that hung reads "This version can't be shown." for 10 minutes.
- Ruling: a view request whose reader moved on is cancelled end to end: TanStack's query `signal` goes through `historyApi.view` to `fetch` (a key change or unmount aborts it), the server drops the handler future, and the init future's drop guard cancels the render's `Progress` (checked by `replay_window` between rows and by `pm_json_diff` between texts; the plain `pm_json` walk and the JSON serialization are linear and not checked) and marks its `StallWatch`, so the stalled gauge shows the thread until it ends. Cancelling is not enough on its own: the diff step's union build and `encode_state_from_snapshot`, the plain `pm_json` walk and the serialization never look at `Progress`, so a dropped request can leave a thread that hangs on with its permit; without a record the next click on that entry would start another one, and with `history.workers` ≥ 2 a few clicks would use up every compute permit (every view 503, every build giving up after `compute_wait`, until a restart). So the drop guard's `Drop`, when the thread still runs, spawns a stall watcher (`tokio::runtime::Handle::try_current()`; none → nothing, as in a test without a runtime) holding the key, the `StallWatch`, `permits` and the deadline `started + timeout` (`started` = the grant): `select!` on `sleep_until(deadline)` and `watch.ended()`; at the deadline, if the thread still runs, it records the timeout as the init would (`knot_history_replay_timeouts_total{phase="view"}`, the ERROR log `history view timed out` with `dropped = true`, `timed_out.insert(key)`), then awaits `watch.ended()`; when the thread ends, either way, it sets `knot_history_replay_threads_stalled` from `permits.stalled()`. The init's own timeout path spawns the same watcher past its deadline (only the gauge part), so the gauge also falls when a timed-out thread ends, with the builder off (`history.workers: 0`) as well; `restore_input` uses the same watcher with the `Restore` key — with the default single worker, a reader clicking through five large versions would otherwise queue four renders nobody sees in front of the fifth (FIFO permits) and of the builder. A caller that had joined the dropped render (another reader of the same version) is not cancelled with it: moka re-runs the init for a waiter whose leader's future was aborted (0.12 `value_initializer.rs:103-109, 202-207`), so that caller renders on its own, queued for a permit behind the cancelled thread, which keeps its permit until it notices the cancel (between rows or texts) or ends; it is counted by its own outcome (`rendered`, or `busy` when the cancelled thread outlasts `permit_wait`), and the dropped caller records nothing itself (its future is gone; its watcher may later record a timeout); cancelling only when no one else waits would need a joiner count per key next to moka's own and saves one replay in a rare case — cost if wrong: a joined caller pays one more replay, and with workers ≥ 2 a version that hangs can start two threads (the dropped one and the re-run) before the watcher records it; after that, none.
- Ruling: "Restore here" sends the `ended_at` of the version the reader sees (`?ended_at=`), and the server answers 409 `history.moved` when the entry has moved on since (compared after the replay, against the `ended_at` read in the read transaction that loaded the replay's input (committed before the render), so the check and the restored state agree); the client then shows `This entry changed while you were reading it. That residual is accepted and recorded in the deviation notes: it needs a gap credit landing on a session that is still open, and the gap content is real page content; a token that sees it (`updated_at` in the view body) would also move on every word-count write and re-pend, answering `history.moved` for unchanged text in the seconds after a session seals, and the list JSON (binding, "After M1.3") has no field for the client key — cost if wrong: one wasted replay per moved restore; in the residual, a restore that includes a gap's text.
