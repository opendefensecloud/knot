# Page history M1.4: timeline UI, version view and Show changes (implementation plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** From the combined page-history release on, the History drawer is the design's timeline: day headings, one entry per editing session (and per restore, copy, import, template, gap and pre-rollout version) with who, when and how many words, loaded as the editor scrolls; clicking an entry shows the page as it was right after it, rendered read-only with the real editor styles, with that entry's own changes highlighted; the old snapshot list and its 5 + 1/day snapshot retention are gone (the 3 newest snapshots per page are kept as a boot cache, plus the newest one boot trusts and those the history builder has still to check).

**Architecture:** The server renders every past version as ProseMirror JSON (`pm_json`, parity-tested against y-tiptap's `yXmlFragmentToProsemirrorJSON`) from M1.3's window replay (`pass::replay_window`), and "Show changes" as the same union-doc diff the stored word counts come from (`diff::entry_diff`), so no Y data for a past state reaches the client. A `Views` service in `crates/knot-history` loads an entry's replay input inside a read-only transaction, renders it on an isolated thread holding a compute permit of the builder's shared `HistoryPermits` (whose builder pacing no longer holds compute permits, so a view waits only for the computes running or already queued when it arrived, at most one builder compute per worker), and caches serialized results keyed on the entry's `updated_at`; a page whose history an older builder version built is refused (409 `history.rebuilding`) until its rebuild. The web drawer is rebuilt in `web/src/features/docs/history/` on the keyset list API (M1.3) and a read-only Tiptap editor built from the live schema plus `historyInsert`/`historyDelete` marks and a `historyChange` node attribute.

**Tech Stack:** Rust (yrs 0.27.3, sqlx 0.9, tokio, axum 0.8, moka 0.12), Postgres 18, React 19 + Tiptap 3.31.3 + @tiptap/y-tiptap 3.0.9 + TanStack Query 5 + valibot (web/), vitest, Playwright (e2e/), Helm chart docs.

## Review Focus

1. **A view asked for while the builder is busy, or while the reader clicks quickly through versions** (the post-upgrade backlog: 20 passes queued per loop, the default single worker, pacing sleeps). The editor expects the version within seconds, not after the queue drains or behind renders nobody looks at any more. The bound is the computes running or already queued for a permit when the view arrives: earlier views, plus at most one builder compute per worker (builder slots), which for a large page's genesis can outlast the client's retries (Rulings). One reader, bot or API key must not hold every compute permit either: its cache-miss renders run one at a time and its further requests wait outside the compute queue (Rulings on rate limits). Pinned in Task 4 (`a_view_waits_for_at_most_one_builder_compute_per_worker`, `a_view_queued_after_a_builder_waits_for_its_compute`, `pacing_holds_the_builder_slot_not_the_compute_permit`, `the_lease_is_renewed_while_the_build_waits_for_a_permit`), Task 5 (`a_busy_permit_is_busy_after_the_wait`, `a_dropped_view_request_cancels_its_render`, `one_principal_renders_one_version_at_a_time`, `a_caller_never_waits_on_another_principals_slot`), Task 6 (`one_user_renders_one_version_at_a_time`, `a_colleague_opening_the_same_version_is_not_blocked`) and Task 12 (`a superseded view request is aborted`).
2. **An open session that grows while the drawer is open.** Its `end_rev` rises, so it can move above a page cursor the client already used, and its view must follow its new end, not a cached older one. The entry must not vanish from the timeline, its view must show the latest text without blanking the pane in between, and a restore must not restore text the reader has not seen. Pinned in Task 5 (`an_open_sessions_view_follows_its_new_end`), Task 7 (`a_restore_of_a_moved_entry_is_a_409`), Task 11 (`a_session_that_moved_above_the_cursor_reappears_after_the_poll`, `a failed poll keeps the loaded timeline`) and Task 12 (`a_selected_open_session_refetches_when_its_end_moves`, `keeps the old version visible while the new end loads`, which also counts exactly two viewer mounts). Residual (Rulings): a late gap credit raises a session's `end_rev` without moving its `ended_at`; neither the client's view key nor the restore check sees that.
3. **A past version the current editor cannot show as stored, or whose diff cannot be built** (a tag or mark the schema no longer has, an empty page, a mark stored as `true`, an attribute stored as a string, linked or bold inline code from an import, stray text or an empty container the old importer or a merge left, a change inside a code block or inline code, a diff step that fails or panics). The drawer must show the version as the live editor would, a placeholder, or "This version can't be shown.", never crash or blank the drawer, and never fail a version only because Show changes is on. Pinned in Task 1 (`unknown_tags_become_a_placeholder_paragraph`, `unknown_inline_elements_become_placeholder_text`, `root_text_is_flattened`, golden cases `unknown-mark`, `empty-doc`, `import-code-link`, `import-code-bold`, the Import-shape and damaged corpus in `pm_json_matches_y_tiptap_on_the_markdown_corpus`), Task 2 (`changes_inside_code_are_marked`, `an_unchanged_diff_render_is_pm_json_on_every_fixture_case`, `an_added_paragraph_with_unknown_content_keeps_pm_jsons_rules`: the default view is `pm_json_diff`'s output, so each `pm_json` shape rule is pinned for it too), Task 3 (`a_diff_that_panics_falls_back_to_the_plain_render`), Task 5 (`a_diff_that_fails_falls_back_to_the_plain_view`), Task 9 (`every rendered fixture case is viewable`, `linked and bold inline code is strict`, `stray text and empty containers render leniently`, `history marks render inside code blocks and inline code`), Task 12 (`a_version_the_schema_rejects_says_it_cant_be_shown`, `an_empty_version_renders_an_empty_paragraph`, `a_version_with_edited_code_renders_with_changes`, `a version with stray text renders as the live editor shows it`, `a version shown without changes says so`).
4. **A very large page or entry, or an input known to hang.** A view over the plain cap answers 409 with a clear message and no allocation of the whole input; a Show changes view over only the lower diff cap shows the plain version (`changes: false`), so the default view never reads as unviewable for a version that fits the plain cap; plain views and restores use the plain cap, so a page that can be built can still be restored; a render that hangs releases the request after `VIEW_TIMEOUT` while its thread keeps its permit, and the same version is not replayed into the same hang again (a diff that timed out, or a session whose word count the builder could not take, is shown plain; a render that hung in its replay or plain walk answers 500, for Show changes views too, while its thread runs and for the TTL after it ends), also when the reader clicked away before the timeout (the dropped request's thread is watched and recorded once it outlives the timeout); a restore that timed out blocks restores only, never the version's view; a session whose count is still being taken is not mistaken for one whose count failed; a baseline the builder skipped is never replayed. Pinned in Task 5 (`over_the_cap_is_too_large`, `plain_views_and_restores_use_the_plain_cap`, `a_skipped_baseline_is_not_replayed`, `a_render_that_panics_fails_and_one_that_hangs_times_out_and_keeps_its_permit`, `a_plain_timeout_blocks_the_show_changes_view_too`, `a_render_that_hangs_before_the_diff_blocks_both_variants`, `a_timed_out_version_stays_blocked_while_its_thread_runs`, `a_diff_that_hangs_is_not_tried_again`, `a_dropped_render_that_outlives_the_timeout_is_not_replayed`, `a_session_the_builder_could_not_count_is_shown_plain`, `a_session_being_counted_is_not_shown_plain`, `restore_input_is_bounded_like_a_plain_view`), Task 6 (`a_skipped_baseline_is_a_500`, `a_view_over_the_cap_is_a_409`) and Task 12 (`a_too_large_version_says_so`, `a version shown without changes says so`).
5. **The hours after the upgrade, while every page's history is rebuilt by the new builder version** (the fix's `BUILDER_VERSION = 2`): snapshots thinned before the rebuild probed them, a lagging builder or `history.workers: 0`, an older pod's snapshot that boot must skip for the newest trusted one, and drawers opened on pages not yet rebuilt. Content only those snapshots hold must still reach history, boot must keep a trusted base, and a version of a page not yet rebuilt must never show the old builder's phantoms or be restored from them: it says the page is being rebuilt. Pinned in Task 5 (`a_page_an_older_builder_built_refuses_views_and_restores`), Task 6 (`a_page_an_older_builder_built_answers_409_rebuilding`), Task 8 (`thinning_keeps_snapshots_the_builder_has_not_probed`, `thinning_keeps_at_most_32_unprobed`, `thinning_keeps_the_trusted_snapshot`, `thinning_a_page_not_built_by_this_version_deletes_what_gc_deletes`, `thinning_keeps_what_the_rebuild_has_yet_to_probe`, `a_given_up_page_keeps_what_its_rebuild_has_yet_to_probe`, `a_page_lifted_from_version_1_views_no_phantom`, which views every version after the gap once the page is rebuilt) and Task 12 (`a page being rebuilt says so`); the drawer polls at 15 s, not 5 s, while a page with entries is catching up (Task 11, `keeps polling while the drawer is open`).

Also pinned, beyond the five: a restricted page refuses view and restore to an Editor without a grant, and an entry id of another page never restores (Tasks 6 and 7); an API key views with `read` and restores only with `update`, a bot reaches both by its page role, a view is never rate-limited and a restore is a `write` (Tasks 6 and 7); a rate-limited restore says how long to wait (Task 12); a baseline that may be shifted is viewed and restored from its trusted prefix (Task 8), and Task 8 Step 4 measures what that costs in memory; a page given up at genesis restores its baselines and nothing newer, and the seq restore still works for operators (Task 7, `a_page_given_up_at_genesis_restores_only_its_baselines`); `?changes=` answers a JSON 400 for every bad value and for a repeated key, and so does the restore's `?ended_at=` (Tasks 6 and 7); a page made by Move to subpage names the page it came from, or says the reader can't open it (Tasks 6 and 10); `can_erase` is `false` for owners too (Task 6); below `md`, focus follows the column the drawer shows (Task 12); a builder that gives up its permit wait in the words phase keeps that session's count pending and its page dirty, also on a page the sweep claimed for an idle session (Task 4, with the pass compute let through first so the expired wait is the words phase's); a past version's task checkboxes cannot be ticked in the viewer (Task 9, `a_viewer_task_click_changes_nothing`); every view outcome, the view timeout counter, the stalled gauge and the render histogram are recorded (Task 5), so the README's alert can fire.

## Rulings

- Ruling: M1.4 keeps restore working by re-keying today's Markdown restore from a snapshot seq to a timeline entry, at the architecture's final route `POST /api/docs/{id}/history/entries/{eid}/restore` (Task 7): the entry's state is replayed exactly as its view, serialized to Markdown and sent as `Event::ReplaceWithMarkdown` with source `restore` and meta `{target_entry_id, target_rev, target_ended_at}` (M2's shape, which the list already renders); "Restore as new page" and "Erase from history" are not built — retiring the snapshot list (task brief, architecture milestones M1.4) leaves today's seq restore without any client, and `main` must stay restore-capable between the M1.4 and M2 merges (M2's verified restore ships in the same combined release, so the release itself does not depend on this interim body); the round trip has exactly today's loss profile, and M2 replaces the handler body with the verified revert behind the same request — cost if wrong: one task of server code whose body M2 rewrites; drop Task 7 and the `Restore here` button stays hidden (`can_restore` gates it) if the user accepts a `main` without UI restore until M2 merges.
- Ruling: `GET /api/docs/{id}/history` stops listing snapshots but keeps answering, with a JSON `[]`, through the whole combined release (revised 2026-11-14 for the user's one-release ruling: M2 ships in the same release that 0.9.13 bundles meet during the upgrade, so M2 must not remove it either; it can go only in the release after, once no 0.9.13 bundle can reach a new pod), and the list keeps its M1.3 path `/history/entries` — M1.3's ruling allowed either; moving the list to `/history` would hand a cached 0.9.13 bundle (rolling deploy) a JSON shape its validator does not expect; removing the route is not an option either: `router_with_state` merges `static_files::router`, whose `fallback_service` serves `index.html` with `200` for any unmatched path (`static_files.rs:26-36`), so the 0.9.13 drawer's `apiFetch` would get the HTML as a string and its `snaps.map(...)` would throw during render (`HistoryDrawer.tsx:39-40, 70`); `[]` makes that drawer show "No snapshots yet" until reload. A new bundle that reaches a 0.9.13 pod for `/view` during the rollout gets that HTML too: the view's valibot `parse` rejects it and the pane shows "This version can't be shown." until the pod is replaced — cost if wrong: one trivial handler kept one release longer than needed.
- Ruling: views share M1.3's compute permits, but the builder's pacing sleep holds a builder slot (`HistoryPermits::builder_slot`, `workers` of them, a second, non-compute semaphore) instead of a compute permit, and the builder takes a compute permit per compute instead of once per `build_page` — tokio's `Semaphore` is FIFO, so with the M1.3 arrangement a view queued behind up to `CLAIM_LIMIT` (20) builder tasks per loop and behind every pacing sleep, i.e. minutes during the post-upgrade backlog; with builder slots, at most `workers` builder tasks ever wait for or hold a compute permit, so a view waits for at most the computes running or already queued when it arrived: the views ahead of it plus at most one builder compute per worker (a builder that claimed, loaded and queued before the view goes first, FIFO; with one worker that is one rows-budget pass of up to 10 s, or a genesis bounded only by `REPLAY_TIMEOUT`); views do not jump that queue (a priority gate, i.e. a builder that yields its permit to every waiting view, can starve the builder under steady viewing and adds a second ordering rule to the one FIFO queue; the bounded wait above is enough for a reader); the rule "After M1.3" binds is one *compute* semaphore per process, which holds: the builder slots gate no replay, so this relaxes only the letter of "no second semaphore", and Task 14's deviation note says so; compute permits stay `workers`, so `workers × F × cap` still bounds replay memory (a builder task waiting for its permit holds its loaded input, at most `workers × cap` more, 1× not F×) — cost if wrong: views add CPU beyond `history.cpuShare` while the builder sleeps (they are user-initiated and bounded by `VIEW_TIMEOUT`), and the builder change must keep every M1.3 builder test green.
- Ruling: a builder waits for its compute permit *after* its claim (the claim and the input load need no permit, which keeps the permit queue to computes that are ready to run), so the wait must not outlive the lease: `Run::compute` creates the acquire future once, pins it (`tokio::pin!`) and polls it in a `tokio::select!` loop against `sleep(lease / 3)` and a `compute_wait` deadline, renewing the lease on each tick (dropping a tokio `acquire_owned` future leaves the queue, so a new future per tick would send the builder to the back every `lease / 3`; a lost renewal ends the pass through `lost()`, as today), renews once more when the permit is granted (the compute then gets a full lease, M1.3's `replay_timeout + 30 s` margin), starts the compute's clock only then (the call sites record `knot_history_replay_seconds` from the duration `compute` returns, and pacing adds only that duration, so queueing is neither measured as replay time nor paced), and gives up after `BuildLimits::compute_wait` (default `LEASE`): it then ends the pass `PassResult::Busy` through the new `store::release_unfinished(pool, me, &[doc_id], PERMIT_WAIT, repend_words)` (`release_on_shutdown` generalized: `claimed_by`/`claimed_until` cleared, `failures = greatest(failures − 1, 0)`, `retry_after` NULL, `last_error = $reason`; `PERMIT_WAIT = "waited too long for a replay slot"`). In the words phase the entry was already taken (`take_words_entry` clears `words_pending` before the load, so each count is attempted once), so the same transaction sets `words_pending = true` again for that entry (`repend_words`, the taken entry's id; `&[]` in `genesis` and `pass`) and sets `doc_history_heads.dirty = true` for its page: a wait that expired is not an attempt, and without both the session would keep NULL counts for good. `dirty` is not always set at that point: `claim` never sets it, `release_in` recomputes it (`head_rev > built_rev OR EXISTS words_pending`, `store::release_in`), and the common way a session seals is the sweep claiming an idle open session (`sweep_candidates`' idle arm, `store::sweep_candidates`) on a page the last `release_in` left clean; that pass seals the session and `write_pass` returns `WordsPending` without a release (`store::write_pass`), so a re-pend without `dirty` would leave a page that `claim`'s clean check (`store::claim`) answers `Clean` and the idle arm no longer selects. The statement order is binding (store.rs lock order): the state `UPDATE … WHERE claimed_by = $me RETURNING doc_id` first (its row lock), then the entries re-pend and the heads `dirty` update, both restricted to the returned doc ids, so only the lease holder's pages are touched. In `genesis` and `pass` an expired wait changes nothing else: the page is claimed again because its heads are dirty, a late snapshot or an idle session, all still true. A graceful shutdown (every rolling upgrade) that aborts a pass during that same wait re-pends it too: the taken entry is recorded in `Builder::words_waiting` (`Arc<Mutex<HashMap<Uuid, i64>>>`, doc id → entry id) right after `take_words_entry` and removed when the permit is granted (the compute is then the attempt) and on every return path of the words phase, but not on drop, so an aborted pass leaves it there; `release_on_shutdown(ids)` passes the recorded entries of `ids` as `repend_words` and clears them. A stale record (a pass that ended by a panic between take and grant) re-pends a session at most once more, which only recounts it. The crash marker (`failures + 1`, `retry_after`, `pass interrupted`) is in place during the wait as during every other part of a pass: a process crash while waiting counts as one interrupted pass (M1.3's rule for a crash anywhere in a pass); an expired wait does not count. An unbounded wait cannot happen: a view thread that stalled with the only permit makes builds give up after `compute_wait` each, the stalled gauge says so, and the Helm README's advice (restart when it stays above 0) applies — cost if wrong: during a stall a page is claimed for up to 5 min per attempt and then retried.
- Ruling: views are not paced — a view is a person waiting; pacing exists to protect the tokio runtime from a backlog of builder work — cost if wrong: a user who clicks through many large versions uses up to one core per compute permit for that time.
- Ruling: with `history.workers: 0` the builder stays off but views get one compute permit (`history_permits` gives `max(workers, 1)`) — the incident switch is about builder replays that kill the process; a view is bounded by the cap and `VIEW_TIMEOUT` like before; but only a running builder lifts a page to `BUILDER_VERSION`, so with `history.workers: 0` on *every* replica no page is rebuilt after the upgrade and every view and restore keeps answering 409 `history.rebuilding` (Ruling on refusing older builders' pages); at least one replica must run the builder, which the CHANGELOG and the Helm notes say — cost if wrong: an operator who wanted no replay at all on a replica still gets view replays there.
- Ruling: the view replays an entry with `ReplayMode::KeepDeleted` from the latest checkpoint at or before `start_rev − 1` through `end_rev`, for both `changes=0` and `changes=1` (one loader, the M1.3 word-count loader generalized), and `merge_gap_at_end = (kind == gap) || (meta.gap_credit_rev == end_rev)` ("After M1.3"); baseline entries decode their `doc_history_baselines.state_bytes`; the rollout entry (`kind = 'baseline'`, `baseline_id` NULL, `meta.rollout`) replays the page's `genesis` checkpoint with its `pending_revs` rows re-applied (the pending fallback) and no rows after it — one replay path, and the plain view of a session is the same doc the diff is built on — cost if wrong: a plain view and a restore replay from the checkpoint before `start_rev` instead of the one nearest `end_rev`, so their input holds every row of the session (and the rows between that checkpoint and `start_rev`); the checkpoint policy does not bound that: one author typing for hours with breaks under 20 minutes makes one long window, which the plain cap (Ruling on the view's input caps) turns into 409 `history.too_large` for that entry only.

- Ruling: text formatting the entry applied or removed is not highlighted; the text renders with its formatting as of the entry's end — yrs 0.27.3's `DiffAssembler` applies format items only when seen in the newer snapshot (architecture verified_apis, `types/text.rs:569-680`), and the architecture's LIMITATION already accepts attribute-level changes as node markers only — cost if wrong: a bold-only session shows no highlight (its word counts are 0/0, consistent with the render).
- Ruling: the server drops marks whose name is not in `tools/schema.json` and turns unknown tags into a placeholder paragraph, while unknown node *attributes* pass through — ProseMirror's `Mark.fromJSON` throws on an unknown mark type (prosemirror-model 1.25.11 `index.js:515`), so one stray mark would fail the whole version, while `NodeType.create` builds attrs from the declared ones only (`computeAttrs`, `index.js:2043-2057`) and ignores extras; an unknown element inside a textblock becomes inline placeholder text, not a paragraph (a paragraph inside a paragraph is not valid content) — cost if wrong: content a dropped mark carried renders unformatted.
