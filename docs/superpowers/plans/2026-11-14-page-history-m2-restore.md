# Page history M2: Restore here and Restore as new page (implementation plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** "Restore here" brings a page back to any timeline entry with a verified CRDT revert that changes only what differs, so comments, suggestions and the authorship of unchanged text survive and connected editors update without a reload; "Restore as new page" copies an entry's version into a new page beside the original, through Duplicate.

**Architecture:** The revert is computed in a new pure module `crates/knot-history/src/revert.rs` on the history replay thread, under a compute permit of the shared `HistoryPermits`, in two bounded steps of `Views`: `restore_target` replays the entry (M1.4's `restore_input`, refusing first a version whose revert plan was already recorded too slow) into a `RevertTarget` (its skip-GC state and its `pm_json`), then `Views::plan_revert` builds, from that target and the live room's pending-free export, yrs's own undo of every change since the target on a skip-GC scratch doc with a fresh client id, verifies it against the target's `pm_json`, and falls back to a verified whole-page replace (a typed deep copy of the target's children; yrs's `as_prelim` turns attributes into strings) when the undo does not verify. The room only exports (`Event::ExportForRevert`, with a `content_version`) and applies (`Event::ApplyRevert`, refused as `Stale` when the page changed since the export, otherwise through the existing `ApplyUpdate` path: Ruling 25's pre-check, persist before fan-out, eviction on a failed persist). The server retries a stale revert up to 5 times within one deadline. "Restore as new page" replays the entry through the same `restore_input` into a GC'd state and hands it to `duplicate::run` as a content override.

**Tech Stack:** Rust (yrs 0.27.3 as `Cargo.lock` pins it, `UndoManager`, sqlx 0.9, tokio, axum 0.8, moka 0.12), Postgres 18, React 19 + Tiptap 3.31.3 + TanStack Query 5 + valibot (web/), vitest, Playwright (e2e/), Helm chart docs.

## Rulings

- Ruling: the seq routes (`GET /api/docs/{id}/history` answering `[]`, `GET …/history/{seq}/markdown`, `POST …/history/{seq}/restore` with its `OVERRIDES` row) stay through the combined release, as M1.4 ruled; the architecture's M2 bullet "Remove the Markdown restore, preview and seq-list routes" and the knot-crdt fix plan's "removed by M2, as planned" stay superseded — both of M1.4's reasons still hold in M2: the combined release still meets 0.9.14 bundles during the rolling upgrade (the SPA fallback answers a removed GET with `index.html`), and M2 does not change which pages lack a restorable entry (given up, being rebuilt, `history.workers: 0` everywhere), for which the seq restore is the operator's workaround; the entry restore stops using `ReplaceWithMarkdown`, which stays for imports and the seq restore — cost if wrong: three small handlers and `markdown_round_trip` kept one release longer; the release after removes them ("After M2").
- Ruling: the revert is computed in knot-history (`revert.rs`, pure: no database, no tokio, no knot-crdt dependency), on the replay thread through `Views`, never in the room — the architecture puts it off the room actor (`crates/knot-history/src/revert.rs`), knot-history already owns `pm_json`, the guarded `Replayer` (Ruling 25's underflow pre-check and post-check) and the permits, and the room must not stall live editing — cost if wrong: none; the room's part is two small events.
- Ruling: `Views::restore_input` keeps its `finish(&[u8])` signature (M1.4's tests call it with byte closures); `revert::target` rebuilds the skip-GC doc from those bytes on the same thread (the replay's own doc is dropped before `finish` runs, so the peak is one doc, as for M1.4's restore); because `PLAIN_MEMORY_FACTOR` (40) was measured with the Markdown finish at 39.1, Task 2 case (f) re-measures the replay with `revert::target` and with `revert::copy_state` on the plain and the shifted-baseline page, and raises `PLAIN_MEMORY_FACTOR` or `SHIFTED_MEMORY_FACTOR` (lowering their caps) if either is exceeded — cost if wrong: one decode per restore.
- Ruling: a restore is two bounded computes, not one: the target (`restore_target`, M1.4's `restore_input` replay with the plain cap and `RESTORE_TIMEOUT`) once, then one `Views::plan_revert` per attempt (the revert cap over `target.state.len() + live.len()`, `REVERT_TIMEOUT`, its own permit wait), so a stale attempt redoes only the live part ("H_T_bytes and target_json are cached", architecture step 6); the revert cap is `revert_max_input_bytes`, from Task 2's measured `REVERT_MEMORY_FACTOR` and `REVERT_TIME_CAP_BYTES` (the min of a memory cap that scales with `replayMaxBytes` and an absolute time cap, so a slow revert is refused before it runs rather than after a 10 s timeout), because the plan holds the target and the live page in one skip-GC doc plus a GC scratch for verification; a live page plus version over it answers 409 `restore.too_large` (distinct from `history.too_large`, so the drawer can suggest "Restore as new page", which needs only the plain cap) — the memory rule `workers × F × cap` must hold for every replay thread; the Markdown restore had no cap — cost if wrong: at the default 4 MiB cap, pages above roughly `min(cap × 40 / F_revert, REVERT_TIME_CAP_BYTES) ÷ 2` cannot be restored in place (the CHANGELOG and Helm notes say so); the target's JSON bytes and state (at most the plain cap plus its JSON) and the latest live export are held on the async side between attempts, for up to 27 s, outside the bound; unlike a rendered view's bytes (M1.4), which are answered at once, they wait for the room, the slot and the permit, so the restore-permit Ruling caps them at one restore per principal per pod.
- Ruling (restore permit): each principal runs one restore at a time per pod, in place or as a new page — in M2 a restore takes the principal's render slot twice (`restore_target`, then each `plan_revert`) and `SlotRelease` frees it when each render thread ends, so nothing else serializes a whole restore; the entry restore's `write` class allows a burst of 120, so one editor or API key could stack many concurrent restores, each holding its target and live export through every later wait, memory `workers × F × cap` does not cover. So `Views::restore_permit(principal, deadline) -> Result<RestorePermit, ViewError>` (Task 4): a per-principal semaphore of `RESTORES_PER_PRINCIPAL` (1), in a map `restorers` kept and pruned as `principals` is (`view.rs` `slot_within`), waited for within `min(now + limits.permit_wait, deadline)`, else `ViewError::Busy` (503 `history.busy` + `Retry-After: 5`); `restore_entry` takes it first, before `restore_target`, and holds it until `restore_answer` returns; `restore_as_new` takes it before its replay and holds it until the handler returns (both pinned over HTTP: Task 5's `two_restores_by_one_person_run_one_at_a_time`, Task 6's `a_restore_as_new_waits_for_the_callers_restore`) (the copy's answer, or the request dropped; the state then lives in `duplicate::start`'s task under the duplicate permit, which bounds it); it only nests outside the render slot (a restore waits for it, never for it while holding the slot or a compute permit), so it adds no lock cycle; a version view takes only the render slot, so a view can still take the slot between a restore's target and its plan, which only delays the plan within its permit wait; the 503 is answered before any replay and is not counted in `knot_history_restore_total` (as M1.4's `view_error` answers are not) — the M1.4 `[Unreleased]` bullet "Version views and restores run one at a time per person, bot or API key user (a second one waits for the first, up to 5 s)" stays true only with it, and Task 9 rewords it to name both rules — cost if wrong: a person who starts a second restore while the first runs (a double click, two tabs, a script in parallel) gets "busy" after 5 s; retrying works.
- Ruling: `target.json` is the compact serialization of `pm_json` (`serde_json::to_vec`), compared as bytes — serde_json without `preserve_order` sorts object keys, so equal trees serialize equally, and bytes cost a fraction of a `Value` while they wait between attempts — cost if wrong: none.
- Ruling: what changed since the target is computed as sets of ids, not state-vector ranges: insertions = the blocks the plan doc holds minus those the target state holds (`Update::insertions(true)` of each pending-free encoding, `replay::held`), deletions = the plan doc's delete set minus the target's (`Update::delete_set`) — the architecture's `IdSet::insert(ID::new(c, sv_T[c]), sv_now[c] − sv_T[c])` would count blocks a page holds past a clock gap (pages that lost an edit) as inserted since the target and delete them — cost if wrong: none; equal to the architecture's sets on pages without gaps.
- Ruling: the plan doc and the fallback's scratch doc take a random 32-bit client id (`uuid::Uuid::new_v4()`'s low 32 bits, as yjs ids stay within 2^53), redrawn while the target's or the live state vector names it or a block of either state names it (`Update::insertions(true)` of each, which covers clients whose blocks all sit past a Skip, where the state vector stops); `Replayer` gains `from_state_as(mode, state, client)` for that — the architecture's "fresh random client id", which keeps restored items in their own client range for later blame; the residual: a client that appears only in the room's parked (pending) content is in neither state, since the export is pending-free, so a draw hitting it (about k/2^32 per restore for k such clients) could fill a parked dependency or be refused by the room's past-gap pre-check (500 `restore.apply`); carrying the room's pending claims into the plan would widen `plan_with`, `plan_revert` and `RevertBase` for that chance, so it is documented, not guarded — cost if wrong: one restore in about four billion on a page with parked content fails or misplaces its parked text.
- Ruling: the undo step runs under `catch_unwind`; a panic, an undo that captured nothing although the states differ, an undo that captured more than one update, or an update that does not verify falls back to the whole-page replace, which is verified the same way and persisted with source `restore_fallback`; when it does not verify either, nothing is written (500 `history.restore_failed`) — the architecture's step 5, plus the M1.4 precedent of not letting a yrs panic in an optional step fail the request — cost if wrong: a fallback restore detaches comments on the page; the timeline note and the toast say so.
- Ruling: the undo's update is used only when `undo_blocking` captured exactly one `observe_update_v1` update; several are treated as no undo (fallback), never merged — `undo_blocking` runs one transaction, so one capture is expected (a `revert.rs` unit test asserts it on hand-built pages, and both properties count the captures of every case through `plan_traced`'s `PlanTrace` and assert that no gap-free case captured more than one), and the knot-crdt fix (Ruling 1 of its plan) places yrs 0.27.3's encoding defect in `Update::merge` / `merge_updates`, so production revert code calls neither — cost if wrong: none; a multi-capture undo still restores, through the fallback.
- Ruling: the whole-page replace is a typed deep copy, not yrs's `as_prelim`, against the architecture's "`as_prelim` … is lossless" — in yrs 0.27.3 `XmlElementRef::as_prelim` and `XmlTextRef::as_prelim` store attributes as `HashMap<Arc<str>, String>` filled with `value.to_string(txn)` (`types/xml.rs:360-374`, `XmlDeltaPrelim`), so heading `level` 1 becomes `"1"`, `checked` false `"false"`, `colwidth` [100] a string, and `pm_json` (typed, `attrs_json`) never matches: the fallback would fail verification on nearly every real page; the copy, in one transaction on a GC'd scratch of the live state (fresh client), clears `default` (`remove_range(0, len)`) and for each live child of the target's `default`: an `XmlElementRef` → `insert(XmlElementPrelim::empty(tag))`, then `insert_attribute(txn, key, any)` for each `attributes(txn)` entry whose value is `Out::Any(any)`, then its children recursively; an `XmlTextRef` → `insert(XmlTextPrelim::new(""))`, then for each chunk of `diff(txn, YChange::identity)` (the reading `pm_json` uses: live text only), `insert_with_attributes` of a string chunk or `insert_embed_with_attributes` of an `Out::Any` chunk with the chunk's `Attrs` (typed), and its own attributes as for elements; any other value (a nested shared type in an attribute or a text chunk, an `XmlFragment` child) makes the fallback `Unverified` with the reason; captured by `observe_update_v1` (one update) — cost if wrong: none beyond the code; Task 9 records the deviation.
- Ruling: the room bumps `content_version` (an `Arc<AtomicU64>`) from one keyed after-transaction callback on its doc, registered in `Room::start` without a handle: `doc.inner().observe_after_transaction_with("knot.content_version", move |txn: &mut TransactionMut| if content_changed(txn) { v.fetch_add(1, SeqCst); })` with `fn content_changed(txn: &TransactionMut) -> bool { !txn.insert_set().is_empty() || !txn.delete_set().is_empty() }` — never a stored `yrs::Subscription`: the workspace builds yrs without its `sync` feature (`default = []`), so `Subscription` holds an `rc::Weak` and is `Send` only under `sync` (`observer.rs:106-109`), and a `Room` holding one would be `!Send` and break `tokio::spawn(room.run())`; the keyed `_with` form stores no handle and returns `Result<(), TransactionAcqError>` (yrs 0.27.3 `doc.rs:111-138`, the `define_doc_observer!` macro: `Err` only when a transaction is open on the doc, since it takes the store with `try_write`), which `Room::start` unwraps with `.expect("a room's doc has no open transaction before its actor starts")` — `booted.doc` was just built by the boot and nothing else holds it, so an `Err` is a code defect, and swallowing it would leave `content_version` at 0 for the room's life and let every stale check pass (yrs's own `UndoManager::expand_scope` unwraps the same call); the form keeps the callback for the doc's lifetime (the room never replaces its doc: `Room::start` assigns `booted.doc` once), and needs no `Send` bound without `sync`; it fires at commit step 4, before GC and squash, and builds no event (the transaction-cleanup observer would build a `TransactionCleanupEvent` per commit, cloning both state vectors and the delete set) — the engine's own `changed` rule (`engine.rs:185-186`) without its pending part — instead of an increment in each handler and instead of comparing state vectors: yrs 0.27.3's doc state vector stops at a client's first Skip (`BlockStore::get_state_vector` sets the clock to `skips.clock_start()`), so an edit integrated past a clock gap leaves the doc's state vector read before and after the transaction (`txn.state_vector()`) unchanged (the transaction's own `before_state()`/`after_state()` do differ there, since `transaction.rs:545-555` raises `after_state` by the insert set's clock end, but comparing them is no simpler than the insert set itself), and on exactly the pages that lost an edit a revert planned before it would pass the stale check; every change, inbound, catch-up, boot, server-side or one added later, goes through a yrs transaction, so no path can forget it; pending-only applies (nothing integrated, nothing deleted) do not move it, which is right since the export leaves pending content out — cost if wrong: none measurable (one callback call and two emptiness checks per transaction, no allocation); a missed change would apply a revert computed against an older state, which still merges as a CRDT update but may leave the result off the target (the stale guard is the only defence; Task 3's table test pins every `Event` that changes content — an inbound edit, `ApplyUpdate`, `ReplaceWithMarkdown`, `PatchTaskChecked`, `ApplySuggestion`, `MoveBlocksOut`, an applied `ApplyRevert`, a caught-up row — and a past-gap edit).
- Ruling: the stale check covers what the room has integrated, not what it has not yet seen: between `ApplyRevert`'s catch-up and its persist, a row another replica commits, typing a 0.9.14 pod holds in memory during the rolling upgrade, and edits still on a client before the revert reaches it all merge with the revert as concurrent CRDT edits; text typed inside a block the revert deletes goes with that block (the normal outcome of a concurrent delete, not corruption: every peer converges), and for a fallback restore, which deletes every live child, every such edit goes; serializing that needs a cross-replica lock and client acks the architecture does not have — cost if wrong: edits not yet saved on the server when the restore applies are lost if they are in a part the restore removes, and after a whole-page replace all of them are; that includes the unsent edits of a tab that was offline and reconnects later (the reconnect sync is their only path to the room) and of a 0.9.14 tab during the rollout, not only the second around the restore; the confirm text, the CHANGELOG and the Helm notes say so, and Task 1's `an_edit_inside_a_removed_paragraph_goes_with_it_on_both_peers` pins the outcome.
- Ruling: `Event::ApplyRevert` catches up first (a stored row another replica wrote moves the version), answers `NotCaughtUp` when `catch_up()` returns `false` (a failed read, a rev gap, or a log that does not reach the room's own confirmed rev, `room.rs` `catch_up`), `Stale` when the version moved, and otherwise applies through `Room::on_apply_update` (its body unchanged) with source `restore` or `restore_fallback`, instead of the architecture's "applies R in one transaction and captures it with observe_update_v1, as ReplaceWithMarkdown does" — `on_apply_update` already persists exactly what the apply changed (the effective update) before it fans out that same update, refuses an update Ruling 25's pre-check refuses before applying anything, enforces the nesting limit, and evicts the room on a failed persist ("If persisting fails, the room evicts itself with no snapshot"); a second capture path would duplicate all of it — cost if wrong: none; the fix's "M2 rules on what the user sees" is: a refused revert answers 500 `restore.apply` ("Restore failed") with no fallback attempt (a fallback update names the same live ids); for Ruling 25's pre-check refusal the page is unchanged and the room stays; the nesting limit or a part-way yrs rejection evicts the room after applying, as for `ApplyUpdate` (every editor reconnects and the page reloads from its log, which holds nothing of the revert), and so does a failed persist; `verify` does not check nesting depth itself: `plan` refuses, before the undo and the fallback, a version or a live page nested past `MAX_NESTING` (the nesting Ruling), so every update it returns reproduces a version within the limit.
- Ruling: `plan` refuses (`RevertError::Unverified("nested past the limit: …")`, 500 `history.restore_failed`, outcome `unverified`, nothing sent to the room) when the version (`RevertTarget.nests_too_deep`, computed by `revert::target`) or the live page (`live_doc`, step 1) has a type nested deeper than `revert::MAX_NESTING` under any root, measured iteratively with an explicit stack and at most `MAX_NESTING + 1` levels, as `knot_crdt::nesting::nests_deeper_than` measures it — knot-crdt's `nesting.rs` documents pages stored deeper than the limit before it existed; on such a page the fallback re-inserts every block, `apply_update_measuring` would refuse it after applying and evict the room (every editor disconnected, a 500, again on every click), and the fallback's delete of every live child is the delete shape that module says can overflow a worker's stack; "a verified update reproduces a version the page already held within the limit" fails exactly there. `revert::MAX_NESTING` mirrors `knot_crdt::nesting::MAX_NESTING` (512) because knot-history must not depend on knot-crdt; `crates/knot-crdt/tests/nesting.rs` pins the two equal — cost if wrong: such pages (none the editor makes) restore only as a new page; the Helm notes say so.
- Ruling: `NotCaughtUp` is retried like `Stale` (a rev gap usually closes by the next catch-up), sharing the `REVERT_ATTEMPTS` budget; `ExportForRevert` returns its own catch-up's result (`RevertBase.caught_up`), and an export with `caught_up == false` counts as that attempt's `NotCaughtUp` without planning or applying anything: the next attempt waits `min(NOT_CAUGHT_UP_PAUSE (200 ms), remaining)` and exports again, so a page stuck behind a rev gap costs at most `REVERT_ATTEMPTS` exports and no plan per click (a plan is up to `REVERT_TIMEOUT` on a compute permit the builder and views share, and it would be refused at the apply anyway); an apply that answers `NotCaughtUp` after a caught-up export (a row arrived between the two) is retried at once, as before; when the last attempt ends in it, the restore answers 503 `history.busy` + `Retry-After: 5` (nothing written) with outcome `failed` and a WARN log, never 409 `history.restore_busy` — a database or log problem must not read as "the page kept changing" or count as contention (`stale`) — cost if wrong: none; one more refusal variant.
- Ruling: `Views::restore_target` refuses a version whose `target.state.len()` alone is over `max_revert_input_bytes` with `PlanError::OverCap` (409 `restore.too_large`) right after its replay, before the room is acquired or anything exported, and `revert_attempts` returns at once on a plan's `OverCap`, `TooSlow`, `Unverified` or `View` error (only `Stale` and `NotCaughtUp` are retried) — each `ExportForRevert` encodes the whole live page on the room actor while typists wait (the design's anti-goal "live typing gets slower"), so a page that will be refused must cost no export, and a stale page costs at most `REVERT_ATTEMPTS` exports; for the same reason a version whose `Revert` key is recorded is refused by `restore_target` before its target replay, before any permit is taken, and so before the room is acquired (which can hydrate it) or exported. Two records exist under that key, each kept `VIEW_CACHE_TTL`: timed out (a plan of it ran the full `REVERT_TIMEOUT`; `PlanError::TooSlow`) and over the cap (`restore_target` found the version alone, or `plan_revert` found the version plus the live page, over `max_revert_input_bytes`; `PlanError::OverCap`; a new `Views.over_revert_cap: moka::sync::Cache<ViewKey, ()>` beside `over_diff_cap` (`view.rs:759-762`), built as that one is, with `.max_capacity(OVER_REVERT_CAP_KEYS)` (4,096) and `limits.cache_ttl` as its time to live: no timeout metric, no stall gauge). Such a version is by construction a slow or large page: without the records every click on it for 10 minutes would replay the whole target on a shared compute permit, boot or wake the room and encode the whole live page before answering 409. The over-cap record trades accuracy for that: a live page that shrinks within the 10 minutes stays refused until the record expires (Restore as new page still works); the first click on a small version of a large live page still costs one export, since nothing cheaper bounds the live page's encoded size (the stored log's size overstates it, the latest snapshot can be stale) — cost if wrong: none beyond that; one record lookup per restore.
- Ruling: `ExportForRevert` catches up first (returning that result as `caught_up`; the `NotCaughtUp` Ruling) and exports the engine's pending-free state (`encode_state_as_update(&doc, None)`); content pending in the live room at the export is neither reverted nor shown in the target, so pending content that drains after a revert comes back — the fix's "After this fix" asks M2 to rule; sending `parked.frames()` with the export would make the plan apply rows that can carry text deleted since (the reason Viewers never get them, the fix's Ruling 5), on pages where that content is already invisible; accepted and documented — cost if wrong: on a page that lost an edit, text waiting for that edit can reappear after a restore when its dependency arrives.
- Ruling (epoch): neither restore writes a version replayed at another content epoch than the page's — groundwork for M3 (erase), because M3's erased-id ingress guard cannot catch it: the architecture's guard refuses only an update carrying an erased id with non-Deleted content, while the undo's `ItemPtr::redo` and the whole-page replace both write the version's text under NEW ids (the fresh client), so a target replayed before an erase and applied after it would bring the erased text back into the live page and its log. So: `Restorable<T>` gains `pub content_epoch: i32` (the entry's `content_epoch` as loaded with its rows, `ViewEntry.content_epoch`, the epoch the version was replayed at); `RevertBase` gains `pub epoch: i32` (the room's `content_epoch`, `room.rs:351-353`, fixed for the room's life: an epoch change evicts the room, and `content_version`'s counting from 0 per instance already keeps the restore on one instance); `revert_attempts` takes the version's `epoch` and refuses an export whose `epoch` differs with `RestoreFailure::View(ViewError::Moved)` (409 `history.moved`, outcome `failed`, no plan, no apply: the timeline was rewritten, so the reader reopens it); no check at the apply: the room's epoch never changes, and a persist from a room still at the old epoch after an erase commits fails with KH002 and evicts the room (500 `restore.apply`, nothing stored); Restore as new page: `CopyVersion` gains `content_epoch: i32`, and `apply_once`, right after `insert_page` of the top page (whose FK check takes the parent's row `FOR KEY SHARE`), reads the source's page row (`crate::updates_store::DOC_KEY_SHARE_SQL`, already `pub(crate)`; no row → `DuplicateConflict`) and then its heads row, `SELECT content_epoch FROM doc_history_heads WHERE doc_id = $1 FOR KEY SHARE` (no row = 0, as `store.rs` coalesces it), and answers `DocStoreError::DuplicateConflict` on a mismatch (409 `doc.duplicate_conflict`, nothing written) — never first in the transaction: the binding M1.2 lock order (`migrations/20261107120001_history_heads.sql`: "Every M1.2 path takes the page row first", on which `doc_store.rs` `purge` relies) takes a page row before its heads row, and the heads row's FK is `ON DELETE CASCADE` (`20261107120002_history_heads_fk.sql`), so a purge of the source's parent, holding the parent `FOR UPDATE` (`lock_archive_root`) and cascading into the source's heads row, would wait on a copy that read the heads row first, while the copy's `insert_page(parent)` waits on the purge: a deadlock `retry_on_deadlock` retries only once, and the purge can be the side aborted;   - `#[doc(hidden)] #[derive(Debug, Default, Clone, Copy)] pub struct RevertHooks { pub skip_undo: bool, pub panic_in_undo: bool, pub empty_undo: bool, pub corrupt_undo: bool, pub fail_fallback: bool }` (`panic_in_undo`: the `observe_update_v1` capture callback panics while `undo_blocking`'s transaction commits, so the unwind runs through `TransactionMut::drop`, the UndoManager's after-transaction handler and `UndoManager::drop`'s `unobserve_*().unwrap()`s, as a real yrs panic inside the undo would; `empty_undo`: the undo runs and its captures are discarded; `corrupt_undo`: the one captured update `u` loses its delete set by a byte rewrite through the public API only (yrs 0.27.3's `Update` has no delete-set setter, and `Update::merge`/`merge_updates` are banned here): `let d = Update::decode_v1(&u)?; let ds_len = d.delete_set().encode_v1().len();` (the v1 encoding is the blocks followed by the delete set, and the delete set's encoded length does not depend on its client order), the corrupted update is `u[..u.len() - ds_len]` followed by `[0]` (an empty delete set), and `corrupt` asserts it decodes with `delete_set().is_empty()` and the same `insertions(true)` as `u`; when `u`'s delete set is already empty, the corrupted update is `Update::EMPTY_V1` (the same as `empty_undo` would leave, and the states differ, so it never verifies); on every page the hook is used with (`a_revert_restores_deleted_text_and_removes_added_text`'s and Task 2's case (a)), the undo deletes text the live page added, so the corrupted update keeps that text and fails verification; the private `fn corrupt(u: &[u8]) -> Vec<u8>` is unit-tested (`corrupt_drops_only_the_delete_set`); `fail_fallback`: the fallback's update is replaced by an empty update, so its verification fails).

  - `#[doc(hidden)] #[derive(Debug, Default, Clone)] pub struct PlanTrace { pub undo_captures: Option<usize>, pub undo_panicked: bool, pub undo_unverified: Option<String>, pub fallback_unverified: Option<String> }` (`undo_captures`: `None` when the undo step did not run or panicked) and `#[doc(hidden)] pub fn plan_traced(target: &RevertTarget, live: &[u8], hooks: RevertHooks) -> (Result<RevertOutcome, RevertError>, PlanTrace)` — what the properties count and print by cause; production calls `plan`.
  - `pub fn verify(live: &[u8], update: &[u8], target_json: &[u8]) -> Result<(), String>` — a GC replay of `live` applies `update` with outcome `Applied`, holds no pending content, and its `pm_json` serializes to `target_json`.

```text
1. live_doc = Replayer::from_state(Gc, live)            (Err → RevertError::Live)
   to_vec(pm_json(live_doc.doc())) == target.json        → Ok(Unchanged)
   target.nests_too_deep, or live_doc nests past MAX_NESTING (the same iterative walk)
                                                         → Err(Unverified("nested past the limit: …"))
   (each step below starts with `go_on(its Checkpoint)`; false → Err(Cancelled) at once)
2. unless hooks.skip_undo, [Undo] under catch_unwind (hooks.panic_in_undo panics inside the
   undo's transaction, from the capture callback below):
     t = Update::decode_v1(target.state)                 (Err → RevertError::Target)
     c = fresh client (Rulings): not in t's nor live's state vector, nor a client of
         t's or live's insertions(true) (blocks past a Skip)
     p = Replayer::from_state_as(KeepDeleted, target.state, c); o = p.apply(live).outcome
     o other than Applied (Refused by Ruling 25's pre-check, ApplyError, Undecodable,
       Corrupt: likely on gap histories) → no undo: PlanTrace.undo_unverified =
       "the live state does not apply to the version: {o:?}", go on to step 3 (never
       RevertError::Live or Target here; only step 1's decode of live is Live)
     insertions = held(p) − t.insertions(true); deletions = p's snapshot delete set − t.delete_set()
     mgr = UndoManager::<()>::with_options(Options { init_undo_stack:
           vec![StackItem::new(p.doc().guid(), deletions, insertions)], ..Default::default() })
     mgr.expand_scope(p.doc(), &p.doc().get_or_insert_xml_fragment("default"))
     capture p.doc().observe_update_v1 into a list; mgr.undo_blocking(); drop the subscription
     (fn undo_captures(..) -> Vec<Vec<u8>>, private, unit-tested)
     exactly one captured update → R (hooks.corrupt_undo: R = corrupt(R)); none or several
       → no undo (Rulings: never merged)
     other = the roots other than "default" and "knot_applied_suggestions" whose to_json in p
             before it applied live differs from after (on the fallback path: h against live_doc)
   R exists and [UndoVerify] verify(live, R, target.json) → Ok(Revert { R, Undo, other })
   before step 3: drop p, mgr, the captures (R included) and step 2's verification scratch
   (the step runs in its own scope; only `other`, the trace and live_doc outlive it), so the
   fallback's peak never adds to the undo's (Task 2 case (c′) measures it)
3. [Fallback] fallback: s = Replayer::from_state_as(Gc, live, fresh client); h = Replayer::from_state(KeepDeleted, target.state)
   one transaction on s: clear "default" (remove_range 0..len); copy each live child of h's
   "default" into it with its typed attributes, recursively (the typed-copy Ruling; never
   as_prelim); a value the copy cannot carry → this step fails with its reason; capture it
   [FallbackVerify] verify(live, R', target.json) → Ok(Revert { R', Fallback, other })
4. Err(Unverified(why the undo and the fallback failed))
```
